# Load testing — proving correctness under concurrency

The point of Kassa is not that it works, but that it **provably stays correct under
concurrent load**. This document is how to reproduce that proof and the numbers it produced.

## Method

- Load generated by **[k6](https://k6.io)** over real HTTP (not in-process).
- App run **compiled** (`npm run build && node dist/server.js`) against **PostgreSQL 16 in
  Docker**, pool size `DB_POOL_MAX=20`.
- After every scenario, an **independent drift checker** (`npm run audit:drift`) re-sums the
  entire ledger and reconciles it against the business tables. "Correct" means it reports `ok`.
- Hardware: Intel Core i7-10810U (12 logical cores), 17 GB RAM, Windows 11. Numbers are from
  this documented local setup, **not** free-tier cloud (cold starts and shared CPU make cloud
  latency meaningless as a headline).

## Reproduce

```bash
docker compose up -d db
npm run db:migrate
npm run build && node dist/server.js   # in one terminal

# in another, per scenario:
npm run db:reset && k6 run load/contention.js   && npm run audit:drift
npm run db:reset && k6 run load/idempotency.js   && npm run audit:drift
npm run db:reset && k6 run load/refunds.js       && npm run audit:drift
npm run db:reset && k6 run load/mixed.js         && npm run audit:drift
```

## Scenarios & results

| Scenario | What it stresses | Result |
| --- | --- | --- |
| `contention.js` | 200 buyers race for stock of **100** (all one SKU) | **100 sold / 100 rejected**, `available_qty=0`, never negative → **no oversell**; drift ok |
| `idempotency.js` | 100 requests, **one shared Idempotency-Key**, 30 VUs | `orders=1, payments=1` → **charged exactly once**; drift ok |
| `refunds.js` | 200 concurrent refunds vs a **100000** payment | 100 succeed / 100 rejected, `refunded_sum = 100000` **exactly** → **no over-refund**; drift ok |
| `mixed.js` | 200 req/s for 20s, random SKU from a 500-item catalog | **p95 = 26.88 ms**, **0.00% errors**, ~200 req/s sustained, 3994 checkouts; drift ok |

## Where it failed and what I learned

The first `mixed` run measured **p95 = 5.16 s** with ~2500 dropped iterations — a disaster.
Root cause: every checkout bought the **same** `SKU-BULK`, so every transaction took a
`SELECT ... FOR UPDATE` on the **same inventory row** and they all serialized on that one
lock. The database wasn't slow — my test had accidentally recreated the very single-row
contention that `contention.js` is *designed* to stress.

Real marketplace traffic spreads across many SKUs, so I seeded a 500-item catalog and had
`mixed.js` pick a random SKU per request. p95 dropped **5.16 s → 26.88 ms** (~190×). The
lesson: a throughput benchmark has to model realistic key distribution, or it measures your
lock contention instead of your system.

## Design decisions this exercised

- **READ COMMITTED + explicit `FOR UPDATE`** (not SERIALIZABLE): row locks give deterministic
  contention handling with far fewer aborts. The `contention` and `refunds` scenarios prove
  the locks are correct (no oversell / no over-refund).
- **Consistent lock ordering** (`ORDER BY sku` before `FOR UPDATE`) + **deadlock/serialization
  retry** with jittered backoff (`withTransactionRetry`, retries on SQLSTATE 40001/40P01).
  The 0.00% failure rate under the mixed storm shows nothing fell through.
- **Connection pool** size is a tuning knob (`DB_POOL_MAX`); 20 comfortably served 200 req/s.
