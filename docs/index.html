Money that provably balances — under concurrent load.

Kassa is a marketplace payments backend built on an append-only double-entry ledger. Every charge and refund posts two sides that must cancel; idempotent APIs make a retried checkout charge exactly once; and the correctness is proven with load tests, not promised.

Where it failed — and what I learned

The 5-second p95.

My first throughput run clocked p95 = 5.16 s with ~2,500 dropped requests. Every checkout was buying the same SKU, so every transaction locked the same inventory row and serialized on it — the benchmark had accidentally recreated single-row contention.

Real traffic spreads across products. I seeded a 500-SKU catalog and randomised the buys: p95 fell to 26.88 ms. A throughput test has to model realistic key distribution, or it just measures your worst lock.

Architecture

One checkout, one transaction.

From the lock to the commit, everything runs inside a single database transaction — it either fully succeeds or leaves no trace.

1

Rate limit + validate

Per-IP throttle, then full JSON-schema validation of the request body.

2

Idempotency gate

INSERT … ON CONFLICT DO NOTHING — a duplicate key blocks, then replays the stored response. The work runs once.

3

Lock inventory

SELECT … FOR UPDATE ordered by SKU — serializes buyers, prevents deadlocks and overselling.

4

Post to the ledger

One balanced posting — debit cash / credit merchant_payable — rejected before any write if it doesn't balance.

5

Record + commit

Insert the order & payment, store the idempotent response, COMMIT. Any error rolls the whole thing back.
